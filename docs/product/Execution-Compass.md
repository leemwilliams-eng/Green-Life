# Green Life Execution Compass

## Purpose

This document is a practical check for day-to-day product and engineering decisions.

Use it to make sure short-term work stays aligned with the larger Green Life platform vision.

## The Ball We Keep Our Eye On

Green Life is building toward:

- a mobile product people trust
- a platform with a durable trust layer
- a community-informed product system
- a future web experience
- a service and agent-ready architecture

If current work does not strengthen at least one of those outcomes, it should be questioned.

## Decision Filter

Before starting major work, ask:

1. Does this increase trust, clarity, or usefulness for the user?
2. Does this strengthen the platform, not just a single screen?
3. Does this reduce drift and improve consistency?
4. Does this preserve room for future web, service, or agent interfaces?
5. Does this support the product as a movement, not just a feature set?

## What We Prioritize Right Now

### 1. Mobile Quality

We are still finishing the first high-quality expression of Green Life.

Current emphasis:

- design-system parity
- coherent navigation and screen behavior
- clean trust and confidence presentation
- polished brand expression
- stable testing workflows

### 2. Trust Model Clarity

We should increasingly make the trust model explicit.

Current emphasis:

- source provenance
- confidence labels
- methodology visibility
- badging rules
- community signals

### 3. Platform Readiness

Current implementation work should prepare for broader product forms.

Current emphasis:

- reusable components
- shared tokens
- API-first thinking
- portable screen logic
- reduced dependency on mobile-only assumptions

## What We Should Avoid

- one-off UI decisions that bypass the design system
- feature additions that increase clutter without improving understanding
- coupling core product meaning to a single client or device
- treating community as decorative rather than foundational
- adding breadth that weakens trust
- short-term shortcuts that make web or service portability harder later

## Active Workstreams

### Mobile Foundation

Goal:
Make the current mobile runtime feel complete, coherent, and trustworthy.

### Backend and Data Contracts

Goal:
Turn Green Life from a mock-driven interface into a real platform with stable services.

### Trust Layer Definition

Goal:
Define how sources, confidence, evidence, badges, and community signals work together.

### Portable Surface Planning

Goal:
Prepare the product for web and future multi-interface expression without diluting the mobile experience.

## Working Rules

### When designing

- prefer reusable patterns over custom exceptions
- preserve simplicity, but not at the expense of meaning
- let trust signals stay visible and understandable

### When engineering

- separate platform concerns from interface concerns
- prefer shared data contracts over screen-local assumptions
- keep portable logic out of native-only code when possible

### When deciding scope

- choose narrower, stronger trust over broader, weaker coverage
- preserve strategic options for future interfaces
- build what strengthens the platform story

## Questions to Revisit Often

- Are we making Green Life more trustworthy?
- Are we making it more portable?
- Are we strengthening community participation meaningfully?
- Are we exposing clearer evidence and methodology?
- Are we building something that can live beyond a single app shell?

## Current Execution Order

1. complete mobile design-system alignment
2. harden backend and API contracts
3. define the trust layer more explicitly
4. identify the first web surface
5. prepare for agent and service expression

## Final Reminder

Green Life should not become smaller as it becomes more polished.

The goal is not simply to make a nicer app.

The goal is to build a trustworthy, scalable product system that can move with people into whatever interface comes next.
